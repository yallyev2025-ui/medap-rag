# Этап 3 — Доказательность: Evidence Pack, citations, Verification Layer, Playground

**Цель:** §10–§15, §36 ТЗ + разделы 4, 6, 7, 8, 9, 10, 13 дополнения. Ключевой приоритет ТЗ:
достоверность и доказуемость важнее полноты и уверенного тона.

Предусловие: закрыт чек-лист этапа 2 (есть метаданные, оригиналы в S3, гибридный поиск и диагностика).

## 3.1. Evidence Pack (§11)

```
EvidencePack {
  query, context, evidenceItems[], sourceReferences[], conflicts[],
  unsupportedAreas[], retrievalDiagnostics
}
```

`evidenceItems` — отобранные и дедуплицированные фрагменты с координатами (источник, страница,
раздел, смещения), а не бесконтрольный дамп чанков. Размер пакета ограничен бюджетом workflow (§57).

## 3.2. Citation Engine (§13) и контракт для сайта

Каждый медицински значимый факт трассируем до источника. Citation:

```
citationId, evidenceId, sourceId, sourceTitle, author, page, section,
exactSupportingText, authorityLevel, verificationStatus, url?
```

- `exactSupportingText` — точный фрагмент из источника, подтверждающий утверждение.
- Выдуманные citations запрещены: `sourceId`/`evidenceId` проверяются по базе перед отдачей.
- Эндпоинт Source Viewer: по `citationId` вернуть страницу источника и координаты фрагмента, чтобы
  образовательный сайт показал текст с подсветкой. Внутренний источник — внутренний viewer,
  публичный — дополнительно внешняя ссылка.
- Поддерживается цепочка: **ответ → citation → источник → страница → выделенный evidence**.

## 3.3. Verification Layer (§12, §56.4)

```
Draft → Claim Extraction → Evidence Support Check → Citation Check → Conflict Check →
Numeric/Unit Check → Terminology Check → Unsupported Claim Detection → PASS / REPAIR / ABSTAIN
```

Сначала дешёвые **детерминированные** проверки: валидность схемы; существование id цитаты;
принадлежность фрагмента разрешённому корпусу и пользователю; формат чисел и единиц; обязательные
поля; отсутствие запрещённого source mode. Только затем семантический `CLAIM_EVIDENCE_CHECK`
(GPT-5.4 Mini) — с claim и точным evidence, без лишней истории чата.

Проверяются атомарные claims, а не ответ целиком. При провале: адресный retrieval-repair → повтор
той же атомарной задачи с исправленным Evidence Pack → если evidence недостаточно — abstain или
явный конфликт. Не просить другую модель «придумать ответ».

Заменяет текущий одиночный проход `_verify_grounded` (`rag/generator.py:445`), у которого fail-open
поведение и проверка ответа целиком.

## 3.4. Numeric safety (§14)

Отдельно проверяются дозы, единицы измерения, диапазоны, проценты, лабораторные значения,
даты и возрастные ограничения, если они влияют на смысл. Где возможно — детерминированный парсинг.
Numeric mismatch блокирует неподтверждённый claim.

## 3.5. Hallucination policy (§15)

```
NO EVIDENCE → RETRY RETRIEVAL → ALTERNATIVE APPROVED SOURCE → STILL NO SUPPORT → QUALIFY / ABSTAIN
```

Внутренние знания модели не являются достаточным доказательством для серьёзного медицинского
утверждения, если workflow требует Evidence. Лучше неполный подтверждённый ответ, чем полный выдуманный.

## 3.6. Conflict Engine (§10)

Если два релевантных источника содержательно расходятся — запрещено молча смешивать:

```
Conflict { claim, sourceA, sourceB, difference, contextRecommendation }
```

Пример смысла для UX: «Для ответа на вашей кафедре используется X; в основном учебнике указана
классификация Y».

## 3.7. Контролируемая деградация (§36)

- Vector DB недоступна → не выдавать RAG-ответ как verified.
- Реранкер недоступен → настраиваемый фолбэк + пометка в диагностике (поведение уже частично есть
  в `rag/retriever.py`).
- Сбой верификатора → ответ не помечается verified.
- Таймаут модели → повтор/очередь/контролируемая ошибка.
- Сбой AI-workflow не портит состояние обучения на стороне продукта.

## 3.8. Админка

- **AI Playground**: предмет, source mode, вопрос. В ответе одновременно пользовательское
  представление с цитатами и техпанель: workflow, модель, сколько найдено и использовано, статус
  verification, вход/выход, стоимость, задержка. Переключатель Inspector Mode раскрывает весь
  pipeline (раздел 5 дополнения).
- **Answer Inspector**: запросы студентов по политике хранения — вопрос, предмет, workflow,
  retrieval, Evidence Pack, модель, ответ, citations, verification, latency, tokens, cost, feedback.
  Пометка причины ошибки: `incorrect_answer`, `bad_retrieval`, `bad_citation`, `insufficient_source`,
  `explanation_problem`, `source_conflict`, `evaluation_problem`, `other`.
- **Prompts & Policies**: версионирование и цикл `DRAFT → TEST → EVAL → PUBLISH → PRODUCTION` с
  rollback. Изменение production-промпта без истории версий невозможно.
- **Evals**: кнопка «Добавить в Eval Dataset» прямо из плохого ответа; повторный прогон контрольных
  вопросов; сравнение до/после (§41, §61).

## Чек-лист приёмки этапа 3

- [ ] У каждого медицински значимого утверждения есть цитата с источником и страницей.
- [ ] Клик по цитате открывает фрагмент учебника с подсветкой; текст совпадает с оригиналом.
- [ ] Несуществующий `citationId`/`evidenceId` не может попасть в ответ (автотест).
- [ ] Вопрос без поддержки в материалах → честный отказ, ноль цитат, без выдуманного ответа.
- [ ] Подменённое в тесте число ловится числовой проверкой и не проходит.
- [ ] Два конфликтующих источника → конфликт показан явно, с обеими версиями.
- [ ] При выключенной БД или реранкере сервис деградирует контролируемо, ответ не помечен verified.
- [ ] Playground показывает ответ и техпанель; Inspector Mode раскрывает весь pipeline.
- [ ] Плохой ответ помечается, попадает в eval-датасет, после исправления regression проходит.
- [ ] Промпт правится через DRAFT→EVAL→PUBLISH, откат возвращает предыдущую версию.
- [ ] Доля неподтверждённых утверждений на eval-датасете измерена и записана.

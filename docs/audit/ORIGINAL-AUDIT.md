# Аудит medap-rag

Дата: 16 ноября 2026. Ветка: `claude/document-timeweb-migration-z75kve`. Коммит: `87aed0517a53688420a132612b96c8a842ac4e19`.

## Вывод

Это уже общий AI-сервис MedAP, а не только Telegram-бот: HTTP API, учебники/личные документы, гибридный поиск, проверка ответа, голос, PubMed, документы/видео и интерфейс презентаций. В нём есть сильные механизмы grounding, фильтрации личных документов и ограничения внешних загрузок. Основной CI и дополнительные изолированные проверки проходят. При этом найдены проблема изоляции evidence на границе с сайтом, предупреждения зависимостей, незащищённая до разбора загрузка админки, несогласованный размер аудио и ряд эксплуатационных рисков.

Приоритеты: **P1** — до следующей существенной выкладки; **P2** — плановое исправление. Предупреждение сканера не равно доказанной эксплуатации.

## R-01 · P1 · Evidence API не проверяет владельца личного документа

Совместная находка с **S-01** в отчёте сайта, а не вторая независимая уязвимость.

[`fetch_evidence`](/workspace/medap-rag/app/evidence/viewer.py:39) читает любой BookChunk по id, затем создаёт ссылку оригинала и возвращает `owner_id`. Однако [GET /v1/evidence/{id}](/workspace/medap-rag/app/api/v1.py:411) не получает текущего пользователя, не проверяет владельца и не передаёт owner клиенту. Bearer-token здесь общий для сайта и не устанавливает право конкретного студента.

Страница сайта `/mentor/source?e=…` доступна медицинскому пользователю и показывает полученный ответ без проверки владения. Telegram-обработчик фрагментов, напротив, сравнивает `owner_id` с Telegram-id; это подтверждает ожидаемую границу доступа.

**Воспроизведение:** на локальной настоящей БД созданы синтетические Book/BookChunk с `SOURCE_USER_DOCUMENT` и `user_id=audit-owner-A`; вызов evidence по id без личности пользователя вернул приватный текст. Фикстура удалена. [Лог](/workspace/audit/rag-probes.log), [скрипт](/workspace/audit/rag-probes.py). Полный HTTP-путь через Next не запускался; возможность его вызова проверена чтением кода сайта.

**Исправление:** запрет выдачи приватных данных без проверенного userId; отдельные правила для общих источников и личных документов; проверка до presign S3. Интеграционный тест на двух пользователях и неизвестном id.

## R-02 · P1 · Требуется согласованное обновление зависимостей

Два разных сканирования:

1. Полный список **прямых pinned требований** `requirements.txt`, включая не установленные локально модели: pip-audit вернул **96 записей advisory в 6 пакетах**.
2. **Установленная CI-среда** с транзитивными пакетами и pip: **133 записи в 5 пакетах**.

Эти числа **не складываются**: наборы пересекаются, записи могут иметь разные aliases. Это не 229 доказанных дефектов приложения. Применимость отдельных CVE зависит от используемого пути.

В прямом наборе затронуты:

| Пакет | Версия | Записей сканера |
|---|---|---:|
| sentence-transformers | 5.5.1 | 1 |
| transformers | 4.57.6 | 9 |
| torch | 2.12.0 | 1 |
| Pillow | 11.1.0 | 72 |
| pydantic-settings | 2.14.1 | 1 |
| python-multipart | 0.0.20 | 12 |

В установленном наборе дополнительно затронут aiohttp 3.13.5; pip относится к инструментам установки, а не к HTTP-пути продукта. Pillow и multipart особенно важны из-за входящих файлов/картинок. Предупреждение pydantic-settings относится к специальной конфигурации nested secrets; её применение в проверенном коде не установлено.

Артефакты: [прямые требования](/workspace/audit/rag-direct-dependencies.json), [установленная среда](/workspace/audit/rag-dependencies.json). Для transformers реестр предлагает исправления в 5.x, тогда как репозиторий намеренно держит 4.57.6 ради optimum-onnx. Поэтому простое обновление одного пина может сломать сборку реранкера.

**Исправление:** подобрать совместимый комплект torch/transformers/sentence-transformers/optimum/onnx, обновить парсеры и HTTP-зависимости; заново проверить CPU-образ, ONNX-экспорт, порог реранкера, качество поиска и файлы. Зафиксировать транзитивные зависимости/хеши для воспроизводимости; не отключать TLS/контрольные суммы ради установки.

## R-03 · P2 · Голосовая расшифровка ограничена 2 МБ JSON вместо обещанных 15 МБ аудио

[voice_transcribe](/workspace/medap-rag/app/api/v1.py:645) допускает `ORAL_MAX_AUDIO_MB=15`, но [таблица middleware](/workspace/medap-rag/api/main.py:48) не содержит `/v1/voice/transcribe`. Применяется [общий лимит 2 МБ](/workspace/medap-rag/app/security/body_size.py:43), причём к base64-JSON. Практический предел исходного аудио около 1,5 МБ, ниже заявленного.

**Воспроизведение:** реальный MaxBodySizeMiddleware с таблицей текущих настроек и подставным конечным обработчиком: одно и то же 2-МБ аудио в base64 → **413** на `/v1/voice/transcribe`, **200** на `/v1/evaluate/oral`. Это тест ограничения тела, не вызов настоящего распознавания. [Лог](/workspace/audit/rag-probes.log).

Похожую согласованность нужно проверить для нового `/v1/vision/transcribe`: он также отсутствует среди специальных путей. Отдельное воспроизведение для него не выполнялось.

**Исправление:** единые лимиты endpoint → закодированное тело → декодированный файл; регрессия на границе, чуть ниже и чуть выше лимита, включая chunked/no Content-Length.

## R-04 · P1 · Multipart-загрузка админки разбирается до проверки доступа и размера

[`/admin/sources/upload`](/workspace/medap-rag/app/admin/routes.py:352) принимает `UploadFile = File(...)`, а `is_admin` проверяется внутри функции. FastAPI/Starlette разбирает multipart и размещает файл во временном хранилище до вызова обработчика. Проверка `MAX_UPLOAD_MB=300` при последующем `file.read()` выполняется уже после этой работы.

[MaxBodySizeMiddleware](/workspace/medap-rag/app/security/body_size.py:43) ограничивает `/v1`, но не `/admin`. Аналогично `/admin/playground/oral` читает файл целиком после разбора. На уровне приложения нет раннего общего ограничения admin-body и раннего отказа до multipart parser.

**Риск:** неавторизованная загрузка может тратить место и ресурсы до отказа; один большой запрос или параллельные загрузки способны исчерпать временный диск. Подтверждено устройством маршрута и фреймворка, **не** нагрузочной атакой. Возможно, внешний Timeweb-прокси имеет собственный лимит — его настройки недоступны, наличие такого лимита не установлено.

**Исправление:** проверка admin-сессии до чтения тела в middleware/периметре, потоковый лимит admin-upload до parser, квота временных файлов и гарантированная очистка. Тестировать отсутствие Content-Length, невалидную сессию, прерванную передачу и переполнение.

## R-05 · P2 · У публичного входа админки нет ограничения попыток

[`POST /admin/login`](/workspace/medap-rag/app/admin/routes.py:135) сравнивает пароль и пишет audit, но не использует rate limiter/backoff/ограничение по источнику. RateLimiter применяется к другим API-операциям. Проверка cookie/пароля и constant-time comparison сами по себе хорошие, но не сдерживают перебор.

**Риск:** подбор слабого пароля и большое число записей в журнал/БД. Пароль production неизвестен, успешный подбор не выполнялся. Внешняя защита прокси неизвестна.

**Исправление:** ограничение по IP и общей частоте, устойчивое хранилище счётчиков, задержка/уведомление, длинный секрет и при необходимости дополнительный фактор/закрытый доступ. Избегать блокировки всей админки одним чужим IP.

## R-06 · P2 · Настройка БД по умолчанию шифрует соединение без проверки сервера

`DATABASE_SSL_MODE=require` — [значение по умолчанию](/workspace/medap-rag/config.py:189). Для него [создаётся SSLContext](/workspace/medap-rag/db/session.py:41) с `check_hostname=False` и `CERT_NONE`.

**Риск:** шифрование не удостоверяет сервер; при MITM/подмене маршрута возможно подключение к ложной БД. Это свойство конфигурации, не утверждение о текущей атаке. В проекте уже есть `verify-full`, но он не является безопасным значением по умолчанию. Локальный `disable` в этом аудите использован только для loopback Docker-БД, не для внешней сети.

**Исправление:** `verify-full` и доверенный CA для managed-БД; при частном CA — поддержка корректного bundle. Проверка неверного hostname/сертификата должна завершаться отказом.

## R-07 · P2 · Словарь rate limiter растёт с каждым новым userId и не очищается

[`RateLimiter`](/workspace/medap-rag/app/security/auth.py:42) сохраняет deque на каждый ключ в `_hits`. Старые timestamps удаляются только при следующем запросе того же пользователя; сами ключи не удаляются вообще.

**Воспроизведение:** 5000 синтетических пользователей; время продвинуто на час без ожидания; после запроса нового пользователя в словаре **5001 ключ**. [Лог](/workspace/audit/rag-probes.log).

**Последствие:** постоянный рост памяти с числом уникальных посетителей, сброс счётчиков после рестарта, отдельные лимиты у нескольких процессов. Это эксплуатационный риск; для небольшого постоянного списка пользователей объём мал. Произвольный userId внешнему клиенту доступен только после service-auth, но рост происходит и при легитимных новых аккаунтах.

**Исправление:** TTL/периодическое удаление и верхняя граница локального кеша либо общий Redis-limiter. Проверить окна, конкурентные запросы, рестарт и отказ хранилища.

## R-08 · P2 · Кеш ответов не привязан к версии модели/промпта и допускает UNVERIFIED

В [lookup](/workspace/medap-rag/app/workflows/answer_cache.py:82) ключ включает режим, tier, предмет, source_type, формат, semantic similarity и ids фрагментов, но не версии модели/промпта/политики. Жизнь ответа — до 30 дней. При смене модели или исправлении инструкции ответ с теми же фрагментами может продолжить приходить старый.

[Условие сохранения](/workspace/medap-rag/app/workflows/ask.py:717) — `generated.verified is not False`, поэтому `None` тоже допускается (кроме flagged/truncated). При попадании кеша возвращается сохранённый verification-флаг, но `versions=_versions()` соответствует текущему окружению, а не обязательно версии, породившей кеш. Непроверенный ответ не превращается в verified=true — это важно; проблема в длительном повторении и неверной атрибуции версий.

**Подтверждение:** цепочка по коду и структуре таблицы, не прогон настоящего LLM.

**Исправление:** fingerprint модели/промпта/политики/источников в записи и ключе, исходные versions в ответе; для кеша подтверждённых ответов требовать `verified is True`; определить инвалидирование после переключения книги/правил. Тест «изменили инструкцию → старый ответ больше не отдаётся».

## R-09 · P2 · CI не включает часть уже существующих проверок

`scripts/run_tests.py` запускает шесть pytest-файлов и 21 скриптовый модуль. За его пределами остаются восемь `test_*.py`: два требуют модели/БД, **шесть можно выполнить в лёгкой среде**. В этом аудите все шесть дополнительных модулей успешно выполнены: web_page, pubmed_sources, presentation_images, cpu_budget, ingest_mode, rerank_priority.

**Риск:** изменения этих подсистем проходят обычный CI без их готовой регрессии. Docker с тяжёлыми моделями, full API startup, настоящий retrieval и production gates также не являются частью зелёного лёгкого CI; нельзя из его успеха выводить готовность всей системы.

**Исправление:** добавить шесть лёгких модулей в runner; отдельный smoke полного приложения с подставным model-serving и реальной локальной БД, а тяжёлую модельную/ONNX-проверку — отдельной job на подходящих ресурсах. Согласовать frontend/backend-контракты и лимиты общими контрактными тестами.

## Общие вопросы жизненного цикла и эксплуатации

- Удаление аккаунта сайта не каскадирует в БД AI; best-effort удаление документов может теряться. См. S-09. Это одна общая проблема, не отдельная десятая находка.
- `/health` возвращает статический `ok`; прогрев моделей идёт фоном, инициализация БД — в бот-ветке запуска. Нужен отдельный readiness для БД/моделей и наблюдение за каждым компонентом. Наличие endpoint не подтверждает доступность ответов.
- DNS-проверка URL и сетевое подключение разделены во времени; репозиторий честно документирует отсутствие полной защиты от DNS rebinding. Защита прямых private-IP/редиректов есть. Проверка rebinding в живой сети не проводилась.
- `VERIFY_SOFT_FAIL=True` — намеренное продуктовое решение с пометкой, закреплённое тестами; это не скрытая ошибка, но для медицинского продукта его пределы должны быть явно приняты владельцем.
- Документы ранних этапов отстают от текущего кода. Например, нельзя переносить историческое «в базе только тестовые учебники» на production сейчас: боевой корпус не исследован.
- Нет результатов нагрузочного прогона OCR + retrieval + голос + презентации на ресурсах production. Локальный CPU-тест не измеряет реальную задержку/качество модели.

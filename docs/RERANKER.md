# Реранкер: torch или ONNX int8 — как включить, проверить и откатить

Реранкер самая медленная часть ответа (~25 с на 60 кусков). Здесь два способа посчитать **одну и ту же**
модель `bge-reranker-v2-m3`:

| `RERANKER_BACKEND` | что это | когда |
|---|---|---|
| `torch` (по умолчанию) | как было: 32-битные веса | рабочий вариант |
| `onnx` | та же модель, сжатая в int8, через onnxruntime | быстрее и в 4 раза меньше памяти |

Если ONNX не собран или упал, бот сам продолжает на `torch` и пишет причину в лог.

## 0. Что должно быть в образе
При сборке образа (Dockerfile) по умолчанию создаётся папка `/opt/models/reranker-onnx-int8`.
Если сборка не уложилась по памяти или времени, шаг молча пропускается — смотри лог сборки. Отключить
шаг: аргумент сборки `BUILD_ONNX_RERANKER=0`. Для процессора с VNNI (`lscpu | grep avx512_vnni`)
задай `ONNX_PRESET=avx512_vnni`.

## 1. Снять «до» (бесплатно)
```
python -m scripts.latency_report --days 14
```
Печатает медиану и «худшие 5%» по каждому шагу ответа. Сохрани вывод.

## 2. Собрать вопросы
```
python -m scripts.collect_questions --limit 100 --days 60
```
Файл `eval/questions_real.txt` остаётся на сервере (в git не попадает). Просмотри его глазами.

## 3. Сравнить старое и новое
```
python -m scripts.compare_rerankers --questions eval/questions_real.txt --top-k 10
```
По строке на вопрос: сколько секунд у каждого и какая доля кусков в топ-10 совпала. В конце — среднее
совпадение, худший случай, ускорение и **подобранный порог** `RERANK_SCORE_THRESHOLD_ONNX`.
Ориентир: совпадение 90% и выше и ускорение заметно (1,5× и больше) — можно включать. Сильно ниже —
остаёмся на `torch`.

## 4. Включить
Переменные окружения бота: `RERANKER_BACKEND=onnx` и `RERANK_SCORE_THRESHOLD_ONNX=<число из шага 3>`.
Перезапуск. В логе у шага `retrieval` поле `reranker` покажет, какой путь работает на самом деле.

## 5. Проверить после включения
Подожди день-два и снова: `python -m scripts.latency_report --days 2`. Сравни с шагом 1. Спроси
бота пару составных вопросов (например, про таламус) и убедись, что ответы не стали хуже.

## 6. Откатить
`RERANKER_BACKEND=torch` и перезапуск. Данные и индекс не меняются: сжимается только реранкер, а
модель, строящая векторы для поиска, не затрагивается — перезагружать учебники не нужно. Если
хочется свежего кеша ответов, очисти кеш ответов после отката.

## Дополнение 12.10.2026 (после первого замера на боевом сервере)

- Сервер: AMD EPYC Rome, 11 ядер, инструкции `avx2` без `avx512`/`vnni` — пресет `avx2` (по умолчанию) единственно подходящий; ×1.6 к скорости — реалистичный предел сжатия на этом процессоре.
- Кандидатов реранкеру: быстрый режим 35, глубокий 45; фрагментов в модель: быстрый 10, глубокий 20 (`TIER_FAST_TOP_K`, `TIER_DEEP_TOP_K`; `TIER_FAST_CANDIDATES`, `TIER_DEEP_CANDIDATES`). Таблица «сколько нужных кусков остаётся» в выводе `compare_rerankers` показывает, не теряется ли качество при меньшем числе.
- `compare_rerankers` теперь печатает ещё: совпадает ли лучший кусок, общие в топ-3, корреляцию порядка всех кусков и проверку вопросов вне материалов (порог обязан их отсекать).
- Если совпадение хочется поднять: пересобрать сжатую модель с `--per-channel` (`python scripts/export_reranker_onnx.py --per-channel`, нужно ~8 ГБ памяти; не в работающем боте), затем снова `compare_rerankers`. Включать только если цифры лучше.
- Защита: если сжатая модель отдаст NaN/inf или не загрузится, бот сам уходит на torch (`reranker=torch` в журнале), а не отвечает отказами.
- Прогрев: при старте бот загружает модели фоном, первый вопрос после деплоя не ждёт загрузки.
- Старую torch-модель из образа убирать только после недели стабильной работы onnx: она — запасной путь.

# STUDENT_AI_INTEGRATION_PLAN

Обязательный по §45 и §54 ТЗ аудит существующего репозитория перед крупной
перестройкой: что здесь уже есть, что переиспользуется, чего из ТЗ нет и каким
путём сервис превращается в MedAP Student AI / Evidence backend.

Документ описывает **исходное состояние** (Telegram-бот с RAG на Railway) и
изменения этапа 1. Дальнейшие этапы — в [`plans/medap-ai/`](plans/medap-ai).

## 1. Стек

| Слой | Технология |
|---|---|
| Бот | aiogram 3, long polling |
| HTTP | FastAPI + uvicorn, один процесс с ботом |
| БД | PostgreSQL + pgvector, SQLAlchemy async + asyncpg |
| Эмбеддинги | `sentence-transformers`, `intfloat/multilingual-e5-large` (1024) |
| Реранкер | cross-encoder `BAAI/bge-reranker-v2-m3` |
| Генерация | OpenAI-совместимый API (до этапа 1 — напрямую OpenAI) |
| Парсинг | pdfplumber, python-docx, OCR через tesseract + poppler |
| Деплой | было: Railway + NIXPACKS; стало: Docker на Timeweb App Platform |

Один процесс (`bot/main.py`) поднимает polling и HTTP в одном event loop
осознанно: эмбеддер (~2.2 ГБ) и реранкер (~2.3 ГБ) должны жить в памяти в
единственном экземпляре, иначе не хватит никакого тарифа.

## 3. Что переиспользуется как есть

- **`rag/` — готовое ядро.** Модуль не зависит от Telegram и принимает
  `source_type`/`subject` параметрами, поэтому `/v1` строится поверх него без
  переписывания поиска и промптов.
- **`load_book()`** обслуживает и бота, и веб-админку: у обоих один чанкинг и
  одни эмбеддинги, расхождений быть не может.
- **`db/init_db.py`** делает `create_all` плюс идемпотентные `ALTER` — новые
  таблицы и поля добавляются без отдельного инструмента миграций.
- **Мягкая деградация реранкера** (`rag/retriever.py`) — уже соответствует §36,
  осталось только отражать её в диагностике ответа.
- **Логика дневных лимитов** и разделение учебники/клинреки остаются как есть.

## 4. Дублирование и его устранение

До этапа 1 конвейер «вопрос → ответ» существовал **дважды**: в
`bot/handlers/query.py` (переписывание запроса → роутер интента → поиск →
генерация) и частично в `api/main.py` (`/answer`). Промпты при этом были в одном
месте, а порядок стадий и параметры поиска — в двух.

На этапе 1 конвейер вынесен в `app/workflows/ask.py`. Telegram стал клиентом
этого workflow (§30), `/v1/chat` вызывает его же. `/search` и `/answer` остаются
как v0 для внешнего потребителя (сценарист рилсов в репозитории `medap`), пока он
не переедет на `/v1`.

Выбор модели тоже был размазан: `_model_for(source_type)` в генераторе плюс две
переменные окружения. Теперь модель определяет `TaskModelMap`
(`app/llm/task_map.py`), а `CLINREK_OPENAI_MODEL` помечен устаревшим.

## 6. Структура модулей (§46)

```
app/
  api/            /v1 для образовательного сайта
  orchestration/  intent router: нужен ли дорогой pipeline
  llm/            провайдеры, TaskModelMap, реестр моделей, учёт расхода
  workflows/      бизнес-логика workflow (ask; дальше — recall, vision, …)
  observability/  сквозной request_id и стадии пайплайна
  security/       service-auth, сессия админки, rate limit, audit log
  admin/          закрытая панель и её шаблоны
  retrieval/ evidence/ verification/ memory/ integrations/   — заполняются этапами 2–4
evals/            прогон качества и отчёты
rag/              существующее ядро поиска и генерации
```

Модульный монолит: дробить на микросервисы без измеримой необходимости запрещено
(§46). Отдельным процессом при необходимости выносится только model serving.

## 7. Изменения схемы БД

Добавлены три таблицы (создаются автоматически через `python -m db.init_db`):

- `ai_usage_events` — расход на каждый вызов провайдера (§59);
- `ingest_jobs` — состояние загрузки источника через админку;
- `audit_log` — критичные операции (§33).

Существующие таблицы не менялись. На этапе 2 расширяется `book_chunks`
(раздел, authority, verification, смещения фрагмента) — тоже идемпотентными `ALTER`.

## 8. Изменения конфигурации

Новые переменные окружения (полный список — в `.env.example`):
провайдеры и их цены с версией (`DEEPSEEK_*`, `OPENAI_EVAL_*`, `PRICING_VERSION`,
`USD_RUB_RATE`), `TASK_MODEL_MAP_OVERRIDES`, доступ (`SERVICE_TOKEN`,
`ADMIN_WEB_PASSWORD`, `ADMIN_SESSION_SECRET`, `RATE_LIMIT_PER_MINUTE`,
`MAX_UPLOAD_MB`), воспроизводимость (`PROMPT_VERSION`, `RETRIEVAL_VERSION`) и
бюджеты вывода (`MAX_OUTPUT_TOKENS`, `CLASS_QUICK_MAX_OUTPUT_TOKENS`).

`DATABASE_URL` по-прежнему принимает схему `postgres://` от managed-БД и приводится
к asyncpg автоматически (`config.py`).

## 9. Migration path

1. **Этап 1 (сделано):** Docker и Timeweb вместо Railway; ядро `/v1`; Telegram —
   клиент; провайдеры и TaskModelMap; телеметрия стоимости; безопасность-база;
   каркас админки; этот аудит и прогон качества.
2. **Этап 2:** метаданные и provenance источников, оригиналы в S3, гибридный
   retrieval, Knowledge Base и Retrieval Inspector в админке.
3. **Этап 3:** Evidence Pack, citations с подсветкой фрагмента, Verification Layer,
   конфликты, Playground и Answer Inspector, версионирование промптов, evals из админки.
4. **Этап 4:** учебные workflows, Vision, документы пользователя, Web Research,
   Voice; затем Content Studio, benchmark моделей и production gates.

Детализация и чек-листы приёмки — в [`plans/medap-ai/`](plans/medap-ai).

## 10. Границы, которые не переносятся

- Knowledge State, учебное состояние, планирование и подписки остаются в
  продуктовом backend MedAP; AI-сервис их не меняет (§25, §42).
- Отдельного пользовательского сайта Student AI нет: студент работает через
  основной образовательный сайт, админка — внутренний инструмент.
- Telegram не владеет AI-логикой и не хранит собственную память (§30).

## 11. Обновление аудита — фактический статус этапов 2–4 (текущий)

Раздел 5 выше — снимок на конец этапа 1, оставлен для истории. Здесь — что
реально в репозитории сейчас, с чётким разделением: **код написан и закоммичен**
vs **подтверждено работающим на Timeweb** (последнее проверяет пользователь после
каждого пуша — эта разница явно проговаривалась всю сессию, повторяю здесь, чтобы
не потерялась).

### Этапы 1–3: код готов, пользователь подтвердил рабочим на Timeweb

`/health`, `/admin` (Dashboard, Knowledge Base, Models, Retrieval Inspector,
Playground, Answer Inspector, Prompts & Policies, Evals, теперь System Health),
Telegram-бот, `/v1/chat`+`/v1/explain` — всё отвечало на реальные тестовые запросы
пользователя на Timeweb на момент проверки после этапа 3B. Гибридный retrieval
(BM25+RRF), Evidence Pack с честными citations, Verification Layer — задеплоены и
подтверждены (с оговоркой: на тестовых файлах, не на настоящем корпусе учебников).

### Этап 4A (все 8 пунктов) + Quick Outline: код готов и запушен, живая проверка на Timeweb — ЧАСТИЧНО подтверждена пользователем, не по каждому батчу отдельно

| Батч | Что | Коммит | Живая проверка на Timeweb |
|---|---|---|---|
| 1 | Tutor EXPLAIN/CLASS_QUICK + фикс DIFFERENTIAL/MULTI | `cac3058` | не подтверждена явно отдельно |
| 2 | Recall/Free-recall + repair | `ffaa097` | не подтверждена явно отдельно |
| 3 | Vision/Test Solver | `78a9cdc` | не подтверждена явно отдельно |
| Quick Outline | AI-генерация схемы для сайта владельца | `cd1e225` | не подтверждена |
| 4 | Документы пользователя (§18) | `5920215` | не подтверждена |
| 5 | Web-поиск по URL + SSRF-защита (§19) | `9961de9` | не подтверждена |
| 6 | Голос/Oral evaluation | `8ee34f8` | не подтверждена |
| 4B | System Health | `9340755` | не подтверждена |
| — | Выбор предмета из списка при загрузке | `50bb357` | не подтверждена |

Всё это скомпилировано, прогнано через смоук-тест (14 проверок, зелёный после
каждого коммита) и через отдельные мок-тесты на каждый батч (retrieve()/llm.complete()
замоканы — реальных вызовов провайдеров и реальной Postgres/S3 в песочнице нет).
**Ни один батч, начиная с батча 1, не был явно подтверждён пользователем как
проверенный живьём на Timeweb** — пользователь тестировал явно после этапов 1–3B,
дальше шёл плотный поток «делай следующее» без явного «проверил, работает» между
батчами 4A. Это не значит, что что-то не работает — значит, что это не проверено
мной и не подтверждено пользователем, и именно это надо сделать перед тем, как
добавлять поверх новые крупные фичи (веб-поиск по интернету, PubMed).

### Открытые пункты — статус после батча 8

1. **Настоящий поиск по интернету** — код готов (`app/workflows/web_search.py`, Tavily, `Task.WEB_SEARCH`,
   `POST /v1/web/search`, кнопка «🌐 Найти в интернете» в Telegram), но **неактивен**: `TAVILY_API_KEY`
   пуст, пользователь ещё не зарегистрировался и не прислал ключ. Активируется само, без правок кода,
   как только ключ появится в переменных Timeweb.
2. **PubMed** — сделано (`app/workflows/pubmed.py`, NCBI E-utilities, ключ не нужен, `Task.PUBMED_SEARCH`,
   `POST /v1/pubmed/search`, кнопка «🔬 Искать в PubMed» в Telegram). Живой сетевой тест к NCBI из
   песочницы разработки был недоступен (egress-политика окружения блокирует хост) — проверено
   мок-тестом на реальном формате XML-ответа NCBI, живую проверку делает пользователь на Timeweb.
3. **Recall/free-recall и устная оценка выведены в Telegram** — команда `/selfcheck`
   (`bot/handlers/recall.py`), FSM-визард (вопрос/тема → режим → ответ текстом или голосом).
4. **Настоящие учебники не загружены** — в базе только тестовые файлы. Отдельный
   шаг пользователя, сознательно отложенный с этапа 1 до стабилизации архитектуры.
5. **Плейсхолдеры Content Studio** в навигации админки (`app/admin/templates/base.html`)
   — по-прежнему `<span>`, не ссылка; корректно отражает реальный статус (не
   построено), упомянуто здесь, чтобы не забылось.

### Security-review этой сессии

Отдельным проходом (см. вывод `/security-review` в этом же ответе) проверены
все накопленные за сессию точки, где могла бы быть реальная брешь: SSRF в

`/security-review`, не дублируется здесь.
